# OS-005.1 — Integração futura com Vercel

## Estrutura observada e solução preparada

Leitura local do portfólio: projeto `portifolio-react`, React + TypeScript/Vite, build `tsc -b && vite build`, diretórios `public/`, `dist/` e funções em `api/`. `vite.config.ts` não define uma alteração de diretório de saída. `vercel.json` atual contém headers de segurança e cache para fonts/img, sem rewrites de demos. Nenhum arquivo desse repositório foi escrito.

A opção indicada é agregar **arquivos já compilados** em `public/demos/` antes do build Vite, ou em `dist/demos/` depois do build do portfólio. Vite copia o conteúdo de public para a saída sem incorporá-lo ao bundle de React. Preferência operacional: copiar para a saída final após o Vite, evitando cópias de dezenas de MB nos fontes do portfólio e permitindo trocar somente uma demo. Isso exige um passo explícito de agregação no futuro pipeline; não foi instalado nesse portfólio.

Nesta OS o artefato preparado fica **somente neste repositório**:

```text
artifacts/os0051/
  demos/
    termo/
    agenda/
    zookids/
    medlive/
  manifest.json
  vercel.demos.fragment.json
```

Não há index de catálogo na raiz. O pacote não contém fontes, node_modules, Laravel, `.env`, credenciais, template MedLive ou Horóscopo bloqueado. O manifesto lista hashes de cada arquivo por aplicativo. As faixas de áudio originais tornam o pacote relativamente grande; os tamanhos reais constam do manifesto. Não se recompactaram/redesenharam assets nesta OS.

## Comandos locais

```sh
# Build com dependências de cada app já instaladas nas respectivas pastas:
node scripts/build-demos.cjs --include-template
node scripts/prepare-demos.cjs
node scripts/demo-server.cjs 8091
```

Abrir `/demos/termo/`, `/demos/agenda/`, `/demos/zookids/` e `/demos/medlive/` em `http://127.0.0.1:8091`. A raiz retorna 404 deliberadamente. Servidor é ferramenta de teste, não produção. O template preservado é testado separadamente em `/_preservacao/medlive-template/`, não fica montado pelo servidor público local.

Para atualizar uma demo sem recompilar outras:

```sh
node scripts/build-demos.cjs agenda
node scripts/prepare-demos.cjs
```

Agregação lê os artefatos já existentes dos demais apps; não compila o portfólio ou os outros aplicativos. O script só substitui seu staging identificado por marcador, recusa destino anterior sem marcador e não aceita caminho externo para o portfólio. `artifacts/` é ignorado no Git.

Cada app tem seu prefixo padrão em app.config.js. `DEMO_BASE_PATH` pode sobrescrever explicitamente; `/` permite build de raiz para diagnóstico. Expo usa baseUrl durante exportação de produção; o servidor Expo de desenvolvimento continua na raiz. Logo, os testes de subpath devem usar a build exportada, não apenas `expo start`.

Agenda, ZooKids e MedLive usam `linking.web.js` para mapear telas e `config.path` para o prefixo. Prefixes sozinho não resolve caminho web no React Navigation. A variante mobile `linking.js` deixa a navegação original sem configuração extra. Ex.: `/demos/agenda/home`, `/demos/zookids/territorios/2`, `/demos/medlive/receitas` e `/demos/medlive/cadastro/foto`. Atualizar essas URLs deve servir o index da própria demo; estado de formulário em memória não é recuperado automaticamente. MedLive restaura os exemplos ao recarregar, como informado no aviso.

## Proposta de configuração, não aplicada

[OS-005.1-VERCEL-EXEMPLO.json](OS-005.1-VERCEL-EXEMPLO.json) é um exemplo para revisão, baseado no arquivo lido. **Não copiar por cima do vercel.json atual sem reconciliar alterações posteriores.** Preserva headers observados e propõe:

- Rewrites específicos por demo para rotas SPA sem extensão.
- Precedência do filesystem para arquivos existentes.
- Nenhum fallback de assets inexistentes em `assets/` e `_expo/` para HTML.
- Nenhuma regra de publicação para Horóscopo/template e nenhum catch-all novo do portfólio.
- Revalidação HTTP dos arquivos de demos; cache immutable de hashes pode ser otimizado numa etapa futura com regras mais específicas.

O portfólio hoje envia `Permissions-Policy: camera=(), microphone=(), geolocation=()` globalmente. Isso impediria recursos web mesmo que o visitante autorizasse o navegador. A proposta separa essa política: somente `/demos/medlive/` permite `camera=(self)` e `geolocation=(self)`, mantendo microphone bloqueado e a política restritiva nas demais rotas. Não basta acrescentar headers duplicados: reconciliar a regra global para evitar conflitos. Permissão no header não equivale a consentimento do usuário; localização da demo continua solicitada apenas pelo botão. Se futuramente houver iframe, permissões também precisarão ser verificadas no elemento e na página ancestral. A integração aprovada usa links.

41 verificações de matching/sintaxe foram executadas com `@vercel/routing-utils@6.6.1`, instalado fora dos projetos. Isso verifica a proposta localmente, não substitui teste real em um deployment autorizado. Não foram usadas credenciais Vercel ou execução de deploy.

Na modalidade de entrega manual via `public/`, os arquivos/pastas a alterar **futuramente**, com autorização, são:

1. `public/demos/termo/**`, `public/demos/agenda/**`, `public/demos/zookids/**`, `public/demos/medlive/**`: copiar o conteúdo gerado correspondente; sem Horóscopo/template.

3. `vercel.json`: reconciliar os rewrites e a política de permissões do exemplo com as regras mais recentes.

Nesse fluxo, `package.json`, `src/App.tsx`, `vite.config.ts`, `components/Projetos.tsx`, `components/ProjectCard.tsx` e `components/ProjectDialog.tsx` não precisam ser alterados: Vite já copia public e os componentes já renderizam links. A publicação Vercel continuará sendo um novo deployment do conjunto estático, mas atualizar uma demo não exige recompilar os outros apps Expo.

A opção de agregar somente após o build Vite exige um passo novo no pipeline do projeto principal: futuramente `scripts/copiar-demos.mjs` (novo) e `package.json` (postbuild ou build encadeado), além de um artefato de entrada versionado e disponível no ambiente Vercel. Esse passo deve copiar `demos/` para `dist/demos/`, validar o manifesto e falhar se o artefato não existir. Não basta usar o caminho local deste computador em um build Vercel. Nesta OS só foi gerado o artefato de entrada; nenhum desses arquivos do portfólio foi criado ou modificado.

Antes de qualquer integração, consultar as [ressalvas de segurança](OS-005.1-SEGURANCA.md). Build funcional não dispensa a triagem dos avisos altos/críticos.
